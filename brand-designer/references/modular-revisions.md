# Modular revisions — focused design review and efficient manual updates

Use when the user wants to change an element of a draft or approved brand system. Read the business record, decision log, current Manual de Marca and source files. Preserve the approved strategy, direction and all unaffected identity elements. Distinguish **approval of a local alternative for consolidation** from **Gate A approval of the updated complete manual**.

## Triage and scope

1. Identify the specific requested change (for example wordmark lettering versus supporting menu typography), its reason, affected applications and dependencies.
2. Confirm which decisions stay unchanged. Ask only if ambiguity materially changes the design; otherwise state the scope.
3. Detect related changes that should be reviewed together (for example typography plus menu hierarchy). Batch them when doing so reduces duplication without obscuring decisions.
4. Reuse existing brand masters, templates, artwork and specifications. Do not re-research stable facts or regenerate the full manual for a small review.
5. Choose the smallest review depth that supports a meaningful choice. **Default Standard**, unless the user chooses another tier or complexity justifies it.

| Depth | Typical pages | Use |
| --- | --- | --- |
| Quick | 1–2 | Minor adjustment; usually 2 alternatives, one context comparison and a brief recommendation |
| Standard (default) | 4–6 | 2–3 alternatives, consistent context applications, technical considerations and comparison |
| Extended | 8–12 | Substantial redesign, multiple dependent elements or additional touchpoints |

These page ranges are guides, not quotas; never pad with filler. A one-page visual comparison can be sufficient for simple decisions.

## Standard focused PDF structure

- Page 1: revision brief, baseline reference, exact scope, fixed elements and success criteria.
- Pages 2–4: Option A/B/C, each shown using **the same mockup types, content, viewing scale, hierarchy and comparable layout**, with actual typography specimens where applicable; reuse identical contexts to avoid confounding the decision.
- Page 5: side-by-side comparison, readability and application fit, accessibility or licensing considerations, tradeoffs and evidence-based recommendation.
- Optional page 6: additional real-world stress test, dependency notes or decision checklist.

Adapt the structure to the selected depth and available alternatives. Use actual PDF/document tools and inspect pages; a single generated collage is not a focused PDF. Do not imply visual samples are final assets. Clearly mark proposed and approved elements.

## Decision and consolidation

- Present options without silently choosing for the user. Record the selected option and approval scope with source/date in the per-business decision log and revision queue.
- Do **not** overwrite the current manual after every small approval. Keep a stable baseline, versioned supplements and approved pending changes.
- When the user completes the review round, reconcile conflicting choices and update the manual **once**, revising all affected pages, technical tables, specimens and mockups consistently.
- Render/inspect the revised manual and maintain the prior draft. Submit the consolidated manual for **Gate A** approval. Only after that approval may final production assets be generated.
- If a revision affects an already accepted manual, create a candidate amendment and seek scoped reapproval before replacing the accepted version.

## Resource discipline and quality

Avoid needless repeated images, full-PDF regeneration, tool calls and research. Use low-cost text comparisons for initial narrowing when visuals are not yet needed, but provide contextual visual comparisons when requested. Resource savings are relative, not guaranteed token quotas. Ensure revision PDFs open correctly, links resolve, typography remains readable, mockups match the same master assets and no unrelated approved decisions are altered. Log any missing capabilities or unverified technical claims.
